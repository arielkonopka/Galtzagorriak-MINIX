# Security review 2026-11-16: kernel and drivers

Scope: everything in the kernel image that handles input from outside the
device, on `main` at `2008709` (after R6.4 part 1). Threat model and method:
[README.md](README.md). Reviewed: `flipper/hal/flipper/usb.c`,
`flipper/vendor/libusb_stm32/src/*.c`, `src/kernel/arm/cons.c`, `tty.c`
(`in_process`, `handle_events`), `arm/disk.c`, `drvlib.c`, the SD card code in
`flipper/hal/flipper/board.c`, `arm/flipdev.c` (IR, iButton, GPIO, ADC,
buttons, backlight), the UART code, `arm/klib.c` (interrupt dispatch,
`task_yield`, the ms timer). Not present yet: BLE/CPU2, CC1101, NFC, RFID,
Wi-Fi (reviewed when they land).

## K1 (High): console input flood holds the TTY task

**Input.** Bytes from a USB host on the CDC port, or on the header UART.

**Failure.** Kernel tasks are not preempted by other tasks (`proc.c`
`ready()`: a task becoming ready joins the end of the task queue). In
`cons_read()` the loop takes input as long as there is some. The USB layer
re-arms the endpoint as soon as the ring has room for a packet, so a host
that sends without pause refills the ring while the TTY task drains it.
With echo on (the login prompt and the shell), each character is also
written to the UART at 115200 baud (87 us busy wait), so the TTY task
consumes about 11 kB/s while USB delivers up to 1 MB/s: the loop never
ends. Second path: a host that sets DTR, sends, and never reads the IN
endpoint made every echoed character wait its full 20 ms (`USB_WAIT_MS`)
for room, again for each byte of a refilled ring. Third: even when
`cons_read` returned, `handle_events()` loops while `tty_events` is set,
and the USB interrupt sets it for every new packet. In all three, no
process runs (the launcher freezes), the clock task cannot kick the
watchdog, and the board resets after 2 s. Simply pasting a large file into
the terminal does it.

**Fix (this PR, no RAM change).**
- `cons_read()` and `handle_events()` stop after a 2 ms slice
  (`TTY_SLICE_MS`, `tty.h`); the rest waits for the next clock tick
  (`force_timeout`, the existing TTY wake-up), so a flood gets at most about
  12 % of the CPU and the processes and other tasks run.
- After one 20 ms wait for USB room times out, further echo and kernel
  output to USB is dropped at once (`usb_stuck`) until the host makes room
  again. `uart_held` became a byte, so the new flag costs nothing (kernel
  RAM 14792 B before and after).

**Test.** `tools/conflood.py` checks the slice in QEMU (processes keep
printing during a 10 s flood, the shell answers after). It cannot
reproduce the original reset: QEMU's UART feeds the guest slower than it
drains. On the Flipper: `cat /dev/urandom > /dev/ttyACM0` at the login
prompt; before the fix it reset the board within seconds, after it the
launcher stays usable (user to confirm on hardware).

## K2 (Medium): extended partition chain loop, unclipped logical partitions

**Input.** The partition tables on the SD card (damaged, or written by
another device).

**Failure.** `extpartition()` follows the "next" entry of each extended
table until it is 0. A chain that points back to itself (or a cycle) with
no logical partitions never ends: the disk task reads forever, so the
watchdog resets the board (or, where the card's busy waits yield, the FS
waits for the disk task and the system hangs), at every boot while the card
is in. Logical
partitions were also not clipped: base + size could lie outside the
extended partition and wrap around 32 bits (an alias of other sectors,
e.g. the MBR). A primary entry starting past the card wrapped its byte base.

**Fix (this PR).** At most 16 extended tables are followed
(`NR_EXT_LINKS`); every logical partition is clipped into its extended
partition without wrap-around; a primary start past the card is clipped.

**Test.** `make -C flipper/tests/host` runs `parttest`: five crafted cards
(self loop, cycle, logical outside, wrap-around, subpartitions outside)
and 20000 random ones; the old code fails three of the crafted ones.

## K3 (Medium): SD card that stops answering holds the CPU

**Input.** The SD card's SPI responses (a worn or broken card, a bad
contact).

**Failure.** `sd_read_data()` and `hal_disk_read_part()` wait up to 500 ms
for the data token with the card selected and without giving the CPU back;
on failure `sd_trouble()` retries at once, up to 5 tries: 2.5 s with no
other task running, past the 2 s watchdog. Card initialisation polls
ACMD41 for up to 1 s the same way.

**Fix (this PR).** `sd_trouble()` gives the CPU to the other tasks between
tries (the card is deselected there, as in `sd_wait_ready()`); the data
token wait is 250 ms (the SD spec allows 100 ms); the ACMD41 loop yields
between tries. Worst stretch without a yield: about 250 ms.

**Test.** None on a PC (needs a model of the SD card's SPI behaviour);
reviewed statically. Hardware check: a card pulled during `cat` of a big
file must give I/O errors, not a reset.

## K4 (Critical, known): root shell for any USB host

`flipper/rootfs/etc/passwd` ships `root::0:0` and `getty` runs on the
console, which is also the USB CDC port and the header UART. Plugging the
Flipper into any computer (or a malicious charger that enumerates as a
host) gives a root shell, and with it everything (flash, keys, canary
logs). This is report S4, specified as R3.4 (Phase 3: root password set in
the first-boot wizard before the login prompt appears on USB). It stays the
top item for the device's threat model; recommended to pull R3.4 forward.
Interim option for the user: no `getty` on the console until a password is
set.

## K5 (Medium): halted IN endpoint stops console output

A host may send SET_FEATURE(ENDPOINT_HALT) for the CDC IN endpoint
(`usbd_process_eptrq` accepts any `wIndex`). If a packet was in flight,
`tx_busy` stays set: no completion ever comes, and CLEAR_FEATURE does not
reset it either. While the port stays open (DTR) `hal_usb_room()` reports
the ring as full, so processes writing to the console wait forever (echo
and kernel output no longer do, after K1). Recommendation: reset `tx_busy`
and `last_full` when the host clears a halt or re-opens the port
(SET_CONTROL_LINE_STATE), and treat a ring that has not moved for a few
seconds while open as "nobody listening" (drop oldest, as with no DTR).
Not fixed here: it changes console semantics; the user's call.

## K6 (Low, by design): one console for USB, UART and LCD

All three are `tty_table[0]`. A host on USB can stop the console's output
with ^S (IXON) and send SIGINT/SIGQUIT to its foreground process group.
Fine for a development console; spec 11.2 already drops the console in the
USB canary profile. Note for the GUI: apps should not depend on
`/dev/console` output.

## K7 (Low): IR receiver keeps the CPU awake

The IR edge interrupt is armed from boot even with no reader, and
`flipdev_idle()` returns 0 while a frame is active, so any IR source (a TV
remote held down, an IR flood) keeps the system out of tickless idle and
Stop2. Battery only. Recommendation: arm EXTI0 only while `/dev/ir` is open
(or a canary listens).

## K8 (Low): CSD v1 capacity

`sd_nsectors = (c_size + 1) << (c_size_mult + 2 + read_bl_len - 9)`: a
`read_bl_len` below 7 or above 11 gives a negative or too large shift
(undefined). Only the capacity is wrong; `disk.c` clips it and reads past
the end fail. Clamp `read_bl_len` to 9..11 when convenient.

## Looked at and fine

- **USB control path** (`usbd_core.c`, `usb.c`): SETUP length checked,
  OUT data limited to the 120-byte buffer, IN data clipped to `wLength`,
  string index checked, SET_LINE_CODING length checked (R4a.7),
  `ep_read` truncates to the buffer, endpoint numbers masked to 0-7.
  `usbtest` drives 2 million random host steps under ASan/UBSan: no memory
  error, no oversize packet, every bulk byte delivered once and in order.
- **UART**: overrun/framing/noise errors cleared on every read; the
  receive interrupt is off while the ring is full.
- **IR receive**: ring indices are bytes on a power-of-2 ring, overflow is
  flagged, a duration cannot encode as the start/end markers, the reader's
  buffer is re-mapped for each value (`numap`).
- **iButton**: 72 bit slots, each at most 70 us masked; a shorted or
  silent line gives `ENODEV`/`EIO` (ROM CRC). The ~6 ms total busy time in
  the device task is an open responsiveness follow-up, not a safety issue.
- **GPIO, ADC, buttons**: no interrupt from the header pins, fixed-size
  output, button events in a bounded ring.
- **Interrupt dispatch**: a spurious or unhandled line is disabled.
- Report S1, S2, S3, S6, S12 (local attacks) have regression tests in
  `flipper/tests/` run by M2/CI.
