# Security review 2026-11-16 (weekly run 1): FS server against damaged file systems

Scope: no driver or input path changed on `main` since the kernel review
(`de89d3e`), so this run took the next item of the planned order: the FS
server (`src/fs/`) reading a file system from the SD card that is damaged
(worn card, power cut during a write by another system, a card from
another device). Threat model: [README.md](README.md). A card crafted by an
attacker is out of scope (it holds the root file system); a damaged one must
not stop the system.

Reviewed: `super.c` (`read_super`, `alloc_bit`, `free_bit`), `read.c`
(`read_map`, `rd_indir`), `cache.c` (`free_zone`, `rw_block`), `inode.c`
(`free_inode`), and every `panic()` in the FS server (29).

## Summary

| # | Severity | Problem | Status |
|---|---|---|---|
| F1 | Medium | A zone number out of range in an indirect block: `rd_indir()` panicked, reading or deleting the file stopped the whole system | **fixed**, QEMU test |
| F2 | Medium | Freeing a zone or inode whose bit is already clear (stale or wiped bit map, two files sharing a zone): `free_bit()` panicked | **fixed**, QEMU test |
| F3 | Medium | `read_super()` did not check that the bit maps cover all inodes and zones, nor where the data zones start: freeing a bit could clear one in the inode table or a data block (corruption) | **fixed**, QEMU test |
| F4 | Low | Direct zone numbers in an inode are not range checked: a damaged inode reads other blocks of the same partition as file data | open, info |
| - | - | The remaining panics are internal consistency checks (buffers, messages) or the root file system at boot ("Bad root file system"), not reachable from a damaged non-root card | ok |

## F1: junk in an indirect block halts the system

`rd_indir()` printed "Illegal zone number" and called `panic("check file
system")`: a single bad indirect block on any mounted file system (also
`/usr`, `/home`, a second card) stopped the Flipper, and again after every
reset as soon as the file was touched. Now the entry is treated as a hole
(the file reads zeros there), the message ends with "run fsck", and a write
or truncate replaces the entry. Test: `tools/fsdamage.py` F1 writes 1 KB of
junk over a file's indirect block; the old FS stops the system at `cat`.

## F2: freeing an unused bit halts the system

`free_bit()` panicked with "tried to free unused block/inode". Removing a
file from a file system whose bit map was wiped, or where two files share a
zone, stopped the system. Now the map is left as it is and one line is
printed ("FS: freeing unused zone bit N on device M/m: run fsck"). Test:
F2 wipes the zone bit map under a 12 KB file and removes it.

## F3: super block layout not checked

`read_super()` checked only that the counts are non-zero. With a zone map
too small for `s_zones`, `free_zone()` (which checks the zone against
`s_zones`) let `free_bit()` compute a block past the map: it cleared a bit
in the first inode block or a data block. Now a file system is refused
("FS: inconsistent super block, not mounted") unless the inode map covers
every inode, the zone map every zone, the data zones start after the inode
table and before the end; `free_bit()` also ignores a bit past its map.
File systems made by `mkfs` and `tools/mkfsimg.py` pass (M2, QEMU boot
with `/`, `/usr`, `/home`). Test: F3 sets the zone map size of a 20000-block
file system to 1; `mount` fails with the message.

## F4 (Low): direct zones not range checked

`read_map()` returns `i_zone[0..6]` as they are. A damaged inode can point
into the inode table or another file of the same partition; reading the
file shows those blocks. Writes through it go to the zone the inode names
(as on any MINIX). Recommendation for later: check direct zones like
`rd_indir()` does now (cheap, one comparison), together with `fsck` on the
device.

## Tests

`python3 -I flipper/tools/fsdamage.py` (QEMU, `make minix disk` first):
makes small file systems on the reserved swap partition `/dev/hd3`, damages
them with `dd`, uses them, and checks for the messages, no panic and a
shell that still answers. PASS with the fix; the old FS stops the system at
F1. Not in CI yet (about 2 minutes of QEMU; it can join `powercut`'s job).

## U1 (Low, added the same day): exec kept the old registers

Found in the RAM defragmentation analysis (`reports/ram-defrag-analysis.md`
in the project files). `do_exec()` set `sp`, `pc`, `psw`, `control`, `lr`
and `r9`, but `r0`-`r8` and `r10`-`r12` kept the values of the program that
called `exec`: an information leak from a setuid program to whatever it
executes (pointers, partial secrets). Low: nothing reads them on purpose
(crtso takes everything from the stack). **Fixed**: the whole register
frame is cleared before the new values are set. No test (a program cannot
observe its registers before crtso runs without a custom start-up); M2
passes.
